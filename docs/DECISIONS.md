## 1. 产品与玩法

**一句话规则**：60 秒内，用方向键控制你的色块跑动，经过的格子染成你的颜色（可以覆盖别人的），时间到时占格最多的人获胜。

**规则参数**（集中在 `shared/src/constants.ts`，M3 调手感时可能微调）：

| 项 | 值 | 说明 |
|---|---|---|
| 地图 | 32 × 20 格 | 640 格 |
| 服务端 tick | 20 Hz（50 ms） | 一局 1200 tick |
| 倒计时 | 3 秒 | 倒计时期间可预设初始方向 |
| 常速 | 每 3 tick 前进 1 格（约 6.7 格/秒） | 整数定点推进 |
| 冲刺 | 每 tick 1 格，持续 12 tick（0.6 秒） | 约 3 倍速 |
| 冲刺冷却 | 80 tick（4 秒，从冲刺开始计） | 服务端强制 |
| 转向 | 在下一次前进时生效，最多缓冲 2 次 | 允许 180° 掉头 |
| 撞墙 | 停在原地，直到收到可走的方向 | |
| 玩家之间 | 可以重叠穿过 | 见 D-01 |
| 出生点 | 四角，2 人时用对角（左上 / 右下） | 对称公平 |
| 人数 | 2–4 名玩家，另可有最多 8 名观战者 | |

**胜负**：计时结束时，按占格数排名；"已离开"的玩家仍显示在榜上，但不参与胜负。最高分并列时显示"平局"，并列出所有并列者。胜负只认服务端判定。

**识别玩家不只靠颜色**：采用 Okabe-Ito 色盲友好配色，每个座位还有固定的形状标记。

| 座位 | 颜色 | 形状 | 地块纹理（M3） |
|---|---|---|---|
| 0 | 蓝 `#0072B2` | ● | 圆点 |
| 1 | 橙 `#E69F00` | ▲ | 斜纹 |
| 2 | 青绿 `#009E73` | ■ | 网格 |
| 3 | 紫红 `#CC79A7` | ◆ | 横纹 |

角色头顶显示昵称和形状，比分条与结算页也同时显示颜色、形状和昵称。两人局固定使用蓝和橙，这是色觉差异下最容易区分的一对。

## 2. 进入体验

**首页**：自动生成一个随机昵称（如"迅捷的水獭"），可以修改。页面上有两个入口：「创建房间」和「输入房间码加入」。昵称作为偏好保存在 localStorage；身份不保存在这里，见 D-09。

**创建房间**：调用 `POST /api/rooms` 拿到房间码后，页面跳转到 `/r/CODE`，并直接用当前昵称加入，不再二次确认，然后进入大厅。

**大厅**：
- 页面醒目地显示房间码，并提供邀请链接的一键复制。复制优先用 `navigator.clipboard`，失败时退化为选中文本；手机上如果支持 `navigator.share`，额外显示「分享」按钮。
- 玩家列表包括颜色、形状、昵称、房主标记、准备状态和在线状态。观战者单独列出。
- 页面下方是三行规则说明，放在卡片里。

**被邀请者打开 `/r/CODE`**：
- 如果 sessionStorage 中已有这个房间的 token，就自动重连，不打扰用户。
- 否则先请求 `GET /api/rooms/CODE`，按房间状态给出不同提示：

| 房间状态 | 页面表现 |
|---|---|
| 不存在或已失效 | "房间不存在或已失效"，提供「创建新房间」和「返回首页」 |
| 大厅中，有空位 | 确认昵称后点「加入」 |
| 对局进行中 | "对局进行中，你将以观战身份进入，下一局自动加入" |
| 已满 4 人 | "房间已满（4/4），可以观战，有空位时下一局自动加入" |

**开始**：其余玩家点「准备」，房主点「开始」。房主的按钮在条件不满足时会写明原因，例如"等待 小明 准备"或"至少需要 2 名玩家"。满足条件后进入 3-2-1 倒计时。

**结算页**：显示获胜者横幅（或"平局"）、排名、占格数、占比和结束原因。底部有「再来一局」和「离开房间」两个按钮。「再来一局」会让房间回到大厅，并把点击者标记为已准备。在点击之前，其他人仍然停留在结算页，只是能看到"小明 已准备再来一局"，不会被强行切走（见 D-11）。

**命令**：
- `npm start`：构建 client 和 server，然后由一个 Node 进程在同一端口（默认 8080，读取 `PORT`）提供页面、`/api` 和 `/ws`。
- `npm run dev`：Vite 热更新，`/ws` 和 `/api` 代理到用 tsx watch 运行的服务端。

- `npm run sim`：运行回归脚本。

**依赖**：
- 运行时：`ws`、`zod`、`sirv`。
- 开发时：`typescript`、`vite`、`vitest`、`esbuild`、`tsx`、`concurrently`，以及 `@types/*`。
- 不引入 UI 框架、数据库、Redis 或外部素材。

## 4. 消息协议

所有消息都是 JSON，形如 `{ t: '<type>', ... }`。客户端发来的每条消息都用 zod 的 strict schema 校验，未知字段直接拒绝。协议版本号放在 `join.v` 中。

### 4.1 客户端 → 服务端

| 消息 | 字段 | 规则 |
|---|---|---|
| `join` | `v, code, name, token?` | 带 token 表示重连；`v` 与服务端不一致时返回 `OUTDATED` |
| `ready` | `ready: boolean` | 仅玩家，且仅在 lobby 阶段 |
| `start` | — | 仅房主，且仅在 lobby 阶段，需满足开始条件 |
| `input` | `seq, tick?, dir?: 'U'\|'D'\|'L'\|'R', dash?: true` | `dir` 和 `dash` 至少有一个；`seq` 必须大于本连接上次处理的值；`tick` 是目标 tick，M4 启用（见 D-08）|
| `rematch` | — | 仅在 result 阶段有效（任何成员都可触发，回到大厅本身无害）；已回到大厅时重复发送直接忽略 |
| `leave` | — | 主动离开 |
| `ping` | `c` | 客户端发送时刻（单调时钟） |
| `resync` | — | 请求全量快照，每秒最多 1 次 |

### 4.2 服务端 → 客户端

| 消息 | 字段 | 何时发送 |
|---|---|---|
| `welcome` | `you, token, role: 'player'\|'spectator'` | join 成功 |
| `snapshot` | `round, tick, room: RoomView, game: GameView \| null` | join / 重连 / resync / 进入倒计时 |
| `room` | `room: RoomView`（`room.rev` 为单调递增版本号） | 房间元数据有任何变化时，整体下发（数据量很小）；客户端丢弃 `rev` 不大于当前值的消息 |
| `tick` | `round, tick, players: PState[], cells: number[], scores: number[], sum?` | playing 阶段每个 tick 发送；`cells` 是扁平数组 `[idx, owner, ...]`，只含变化的格子；`sum` 每 20 tick 附带一次 |
| `pong` | `c, s, dropped` | `s` 是服务端时间，`dropped` 是本连接累计被丢弃的输入数 |
| `error` | `code, msg` | 见下文错误码 |

数据结构如下：

```ts
RoomView  = { code, rev, phase: 'lobby'|'countdown'|'playing'|'result', hostId,
              round, startsAt, endsAt, soloEndsAt /* 不足 2 人在线时的提前结束时刻 */,
              members: Member[], lastResult: Result | null }
Member    = { id, name, role: 'player'|'spectator', slot: number|null,
              ready, online, offlineUntil: number|null, left: boolean }
GameView  = { w, h, cells: number[] /* 每格存 owner 的 slot，空格为 -1 */, players: PState[], scores }
PState    = { id, slot, x, y, dir, moving, dashLeft, cdLeft, frozen, ack /* 最后处理的 seq */ }
Result    = { round, reason: 'time'|'opponents_offline'|'opponents_left',
              ranking: { id, name, slot, score, left }[], winners: id[], sum }
```

**错误码**：

| 错误码 | 含义 |
|---|---|
| `ROOM_NOT_FOUND` | 房间不存在或已失效 |
| `ROOM_FULL` | 玩家和观战席位都已满 |
| `BAD_MSG` | 消息不合法 |
| `RATE_LIMIT` | 发送过快 |
| `NOT_ALLOWED` | 当前阶段或身份不允许该操作 |
| `TOKEN_INVALID` | 重连凭证无效 |
| `OUTDATED` | 客户端版本过旧，需要刷新 |
| `SERVER_FULL` | 服务端已达全局上限 |

**WebSocket 关闭码**：

| 关闭码 | 含义 |
|---|---|
| 4001 | 同一身份在别处建立了新连接，旧连接被顶替 |
| 4002 | 主动离开 |
| 4008 | 违规（持续超限或反复发送非法消息） |
| 1009 | 消息过大，由 ws 库自动关闭 |
| 1012 | 服务器重启或部署 |

**HTTP 接口**：

| 接口 | 返回 |
|---|---|
| `POST /api/rooms` | `{ code }` |
| `GET /api/rooms/:code` | `{ exists, phase, players, spectators, full }` |
| `GET /healthz` | `{ ok, rooms, conns, tickLagMs }` |

## 5. 同步模型

### 5.1 权威与时间

服务端是唯一权威。服务端用固定步长推进模拟：目标 tick = `floor((now − startsAt) / 50ms)`，主循环用 `setTimeout` 精确对齐到下一个 tick 的时间点，单次最多追 4 个 tick。如果落后更多（进程被长时间阻塞），不再追赶，而是把 `startsAt / endsAt` 整体后移并广播，保证所有人看到的剩余时间仍然一致，同时记录 `tick_overrun` 日志。这样即使 Render 免费实例只有 0.1 CPU、计时器偶尔抖动，tick 节奏也不会长期漂移。每个 tick 的流程是：取出各玩家缓冲的输入，调用 `step(state, inputs)`，算出变化的格子，然后广播。

客户端只发送输入，从不上报位置、分数或结果。玩家身份绑定在连接上，消息里没有"我是谁"这个字段，所以无法替别人操作。

### 5.2 规则引擎

`step(state, inputs) -> state` 写在 shared 中，是纯函数，同时满足以下约束：
- 只用整数运算，不用 `Math.random` 或当前时间。
- 玩家按 slot 顺序处理，结果与输入到达的先后无关。
- 分数随步进增量维护，单元测试会与全图重新计数逐 tick 比对。

服务端模拟和客户端预测共用这一份代码。

渲染层在逻辑格之间做补间：逻辑位置按格跳变，画面在"上一格到当前格"之间平滑过渡。因此转向不会在格子中间突兀地折线。

### 5.3 输入处理（服务端）

- **消息大小**：ws 的 `maxPayload` 设为 1 KB。
- **频率**：每个连接一个令牌桶，每秒 20 条，突发 40 条。超出的消息丢弃并计数；10 秒内丢弃超过 100 条就关闭连接（4008）。
- **seq**：按连接计数（见 D-07）。重复或过期的 seq 直接丢弃，计入 `dropped`。
- **单 tick 上限**：每个玩家每个 tick 最多处理 4 条输入；转向队列最多 2 个，重复的同向输入去重。
- **阶段与身份**：只有 countdown 阶段（预设方向）和 playing 阶段接受输入；观战者、离线者或已离开者的输入一律丢弃。
- **冲刺**：冷却中收到的冲刺请求被忽略，冷却完全由服务端计算。

### 5.4 下行：快照 + 增量 + 校验和

- 加入、重连、请求 resync、进入倒计时这几个时刻，服务端发送全量 `snapshot`。
- 之后每个 tick 发送一条 `tick` 消息，包含变化的格子和全部玩家状态（最多 4 人，每条约 300 字节）。
- **顺序判定**：客户端按 `(round, tick)` 字典序判断新旧。旧的或重复的 tick 丢弃并计数。如果收到 `tick > last + 1`（出现跳号），说明丢了增量，立即发 `resync`。用 `round` 参与比较，是为了避免新一局的 tick 从 1 重新计数时，被误判为旧消息。
- **校验和**：服务端每 20 tick 附带一次全图 FNV-1a 校验和，覆盖格子和玩家位置；结算结果 `Result.sum` 也带一份。客户端用自己重建的权威状态计算并比对，不一致就自动 resync，并在调试面板中计数。
- **慢客户端**：如果某个连接的 `ws.bufferedAmount` 超过 256 KB，暂停向它发送增量，并标记"需要快照"；缓冲排空后补发一次全量快照。

### 5.5 时钟与倒计时

- 客户端每 2 秒发一次 ping，保留最近 8 个样本，取 RTT 最小的那一个估算时钟偏差：`offset = s − (c + rtt/2)`。客户端时间统一用 `performance.timeOrigin + performance.now()`，不受系统时钟跳变影响。
- 倒计时和对局剩余时间都按 `startsAt / endsAt − (now + offset)` 显示。这只是显示用的，真正结束以服务端的 tick 为准。如果本地计时先归零，就显示"结算中…"，等待服务端的结果。
- 网络消息在 `onmessage` 中立即处理，渲染在 `requestAnimationFrame` 中进行。这样即使标签页切到后台、渲染暂停，状态也不会错乱。

### 5.6 渲染：插值与预测（M4）

**其他玩家用插值**：渲染时间取 `估算服务端 tick − 2`（约 100 ms），在缓冲的服务端状态之间插值。如果缓冲不足，就自动把延迟增加到最多 4 tick。

**自己用预测**（见 D-08）：
1. 客户端在"估算服务端 tick + 领先量"上运行自己的预测模拟。领先量为 `ceil((RTT/2 + 抖动余量) / 50 ms) + 1`。
2. 每条输入带上目标 tick，服务端在 `max(当前 tick + 1, min(目标 tick, 当前 tick + 10))` 时刻应用它。
3. 只要估算准确，服务端和客户端会在同一个 tick、同一格转向，几乎不会回弹。
4. 每次收到服务端状态，客户端用 `ack` 对账：以权威状态为基础，重放尚未确认的输入。如果有偏差，用 100 ms 平滑修正，并计入"纠正次数"。
5. 自己预测出来的染色先作为临时层显示，服务端确认后，以权威格子为准。

### 5.7 弱网模拟与调试

**URL 参数**：

| 参数 | 作用 |
|---|---|
| `?lag=200` | 附加 200 ms 往返延迟，上行、下行各一半，保持顺序（与 TCP 一致） |
| `&jitter=50` | 附加随机抖动，同样保持顺序 |
| `&chaos=1` | 额外注入重复和乱序的下行消息，以及重复和过期的上行输入，专门用来演示丢弃逻辑 |
| `&debug=1` | 打开调试面板；也可以按 `` ` `` 键切换 |

**调试面板显示**：
- 网络：RTT 均值和最小值、时钟偏差、上下行字节速率。
- 同步：服务端 tick、本地渲染 tick、插值延迟、预测领先量。
- 异常计数：丢弃的旧 tick 数、服务端报告的丢弃输入数、resync 次数、校验和不一致次数、预测纠正次数。

**调试面板按钮**：连发 3 条重复输入、发送一条过期 seq、断开连接（模拟掉线）、切换 lag 档位（0 / 100 / 200 / 400 ms）。

## 6. 房间状态机与生命周期

### 6.1 状态机

```
lobby ──房主开始（≥2 名玩家，且全部在线、已准备）──▶ countdown（3 秒，下发 startsAt）
  ▲   ◀──────── 玩家少于 2 人（离开或宽限超时） ────────┘ │ 时间到
  │                                                         ▼
  │                                          playing（1200 tick，endsAt）
  │                                                         │ ① 时间到
  │                                                         │ ② 在线玩家 ≤ 1 人持续 10 秒
  │                                                         │ ③ 未离开的玩家少于 2 人（立即结束）
  └──── 任一玩家点「再来一局」 ──── result ◀───────────────┘
        （回到大厅：清空准备状态、点击者自动准备、
          观战者按加入顺序补位、round + 1）
```

- 进入倒计时时，服务端创建初始 GameView，并通过快照下发，客户端立刻能看到出生位置。
- 结算后的房间会一直停在 result 阶段，直到有人点「再来一局」，或者房间被清空。
- Room 的所有状态变更都在同步方法里完成，并且 **Room 内部没有任何定时器**：倒计时结束、tick 推进、30 秒宽限期、单人检测都在 `update(now)` 中按时间戳判定，由 RoomManager 的主循环驱动。这样不存在"定时器触发时状态已经变了"的竞态，单元测试也可以直接传入假时间，不依赖真实计时。代价是单人检测等逻辑有不超过 1 个 tick（50 ms）的误差。

### 6.2 生命周期事件

| 事件 | lobby / result | countdown / playing |
|---|---|---|
| 新人加入 | 有空位就成为玩家；4 人已满时成为观战者，并明确提示；观战席位也满时返回 `ROOM_FULL` | 成为观战者，提示"下一局自动加入" |
| 断线（收到 close，或心跳 10 秒无响应） | 座位保留 30 秒，所有人看到"小明 掉线，重连中 25s"；离线者视为未准备，房主此时无法开始 | 角色原地停住，已染的格子保留；倒计时提示同左 |
| 30 秒内用同一 token 重连 | 先用 4001 关闭旧连接，再绑定新连接，然后发送全量快照，恢复座位和房主身份 | 同左，恢复后可以继续操作 |
| 30 秒宽限期到 / 主动 `leave` | 立即移出房间。如果是房主，按加入顺序移交给下一位在线玩家；没有在线玩家时，移交给下一位玩家 | 标记为"已离开"，格子保留，不参与胜负；如果未离开的玩家少于 2 人，立即结算，原因为 `opponents_left` |
| 只剩 1 名在线玩家 | — | 持续 10 秒后结算，原因为 `opponents_offline`；其间有人重连则取消计时 |
| 倒计时中玩家少于 2 人 | — | 取消对局，回到大厅 |
| 观战者断线 | 同样保留 30 秒，可以重连，但不占玩家座位 | 同左 |
| 房间内没有任何成员 | 5 分钟后销毁。销毁后访问 `/r/CODE` 显示"房间已失效"和「创建新房间」 | 同左 |
| 服务端收到 SIGTERM（部署或重启） | 向所有连接发送 1012 关闭码；客户端提示"服务器已更新，房间已失效"，并提供「创建新房间」 | 同左 |

### 6.3 客户端侧的行为

- **意外断线**（关闭码不是 4001、4002 或 4008，详见 D-22）：显示"连接中断，正在重连…"，并按 0.5 s → 1 s → 2 s → 4 s 指数退避重连，带上 token，总时长不超过 30 秒。
- **刷新页面**：不会发送 `leave`。刷新等同于短暂断线，靠 sessionStorage 里的 token 自动恢复。
- **被顶替**（4001）：显示"你在另一个标签页打开了这个房间"，提供两个选项：「在这里继续」会重新连接并反过来顶替对方；「以新玩家加入」会清除本页 token，然后重新加入。
- **重连失败**（收到 `TOKEN_INVALID` 或 `ROOM_NOT_FOUND`）：清除该房间的 token，引导用户重新加入或创建新房间。
- **版本过旧**（收到 `OUTDATED`）：提示"游戏已更新，请刷新页面"。

## 7. 安全与滥用防护

| 威胁 | 措施 |
|---|---|
| 伪造位置、分数或结果 | 协议里根本没有这些字段，服务端权威计算 |
| 冒充他人 | 身份绑定在连接上；重连 token 为 128 位随机值，按房间隔离，比较时用 `timingSafeEqual` |
| 刷输入、超速、无冷却冲刺 | 令牌桶限流、单 tick 处理上限、转向队列上限；速度和冷却都只由服务端规则计算 |
| 重放或乱序输入 | 按连接递增的 seq，重复或过期直接丢弃 |
| 畸形或超大消息 | `maxPayload` 1 KB、`JSON.parse` 加 try/catch、zod strict 校验；反复出错则关闭连接（4008） |
| XSS（昵称） | 昵称在服务端清洗：trim、去控制字符和换行、限 1–12 个字符、同房间重名自动加后缀。客户端只用 `textContent` 和 Canvas `fillText` 输出，不用 `innerHTML`。另外加 CSP：`default-src 'self'; connect-src 'self' ws: wss:` |
| 跨站 WebSocket 劫持 | 校验 Origin 头，只允许同源（以及开发时的 localhost） |
| 刷房间、猜房间码 | 每个 IP 每分钟最多建房 10 次、查房或加入 30 次，同时最多 8 个连接；全局最多 200 个房间；每间房最多 4 名玩家和 8 名观战者 |
| 静态资源路径穿越 | 交给 `sirv` 处理，不自己拼接路径；SPA 回退只对 `/` 和 `/r/*` 生效 |

**不在范围内**：脚本或外挂级的"完美操作"检测。服务端已经限制了任何人都不可能超出规则，剩下的问题记入"不做"清单。

## 8. 部署：Render

**Render 免费实例的特点**（已于 2026-10-22 核实官方文档）：
- 15 分钟没有入站流量（包括 HTTP 请求和已有连接上的 WebSocket 消息）就会休眠；下一次请求时唤醒，大约需要 1 分钟，期间 Render 会显示一个加载页 [1]。
- 每个工作区每月有 750 小时免费实例时长 [1]。
- 平台可能随时重启实例，并且免费实例只能跑单实例 [1]。
- 免费规格为 0.1 CPU、512 MB 内存 [1]。

**WebSocket 相关**：
- 公网必须使用 `wss://`；所有公网流量（包括 WebSocket 升级请求）都路由到同一个端口，默认是 10000，通过 `PORT` 环境变量提供 [2]。
- Render 对连接时长没有硬性上限，但实例替换时连接会断开；关停前会先发 SIGTERM，给 30 秒宽限 [2]。

**这些特点对本项目的影响和对策**：

| 平台特点 | 对策 |
|---|---|
| 只能单实例，且房间在内存中 | 正好满足"所有房间在同一个进程里"的前提，不会出现多实例间房间分裂 |
| 重启或部署后房间丢失 | README 中写明；客户端会给出友好的失效提示（见 6.2、6.3） |
| 冷启动约 1 分钟 | README 提醒验收者"首次打开可能需要等待约 1 分钟"。评审前由我们手动预热一次；如有需要，可以在评审窗口期用外部定时 ping 保活，单个服务全月运行约 744 小时，在 750 小时额度之内 |
| 0.1 CPU | 固定步长循环带追赶上限；每个 tick 的工作量很小；`/healthz` 暴露 `tickLagMs`，用于观察 |

**Blueprint 配置**（`render.yaml`，字段依据官方规范 [3]）：

```yaml
services:
  - type: web
    runtime: node
    name: turf-rush
    region: singapore
    plan: free
    buildCommand: npm ci && npm run build
    startCommand: node server/dist/index.js
    healthCheckPath: /healthz
    autoDeployTrigger: commit
```

**流程**：
1. 我使用你提供的 GitHub token 创建仓库并推送代码。
2. 你在 Render 控制台中点一次 New → Blueprint，选择这个仓库。这一步需要你本人登录 Render 并授权 GitHub App。我可以先把页面打开到这一步，再交给你接管登录。
3. 之后每次推送到 `main` 分支，Render 都会自动部署。

**时间安排**：第一次部署放在 M1 结束时（见 D-15）。

## 9. 测试与调试

**shared 单元测试**：
- 移动规则：常速、冲刺、冷却、撞墙停住、转向缓冲、180° 掉头。
- 染色、覆盖他人格子，以及增量分数与全图重新计数的一致性。
- 确定性：相同的输入序列跑两次，得到逐字节相同的状态。
- 排名与平局判定、已离开玩家不参与胜负。
- 校验和计算。
- 协议 schema：非法类型、多余字段、超长昵称、seq 越界都会被拒绝。
- 房间码：生成结果只含合法字符；输入规范化（大小写、空格、连字符）。

**server 单元测试**：
- Room 使用假时钟和假连接，第 6.2 节表格里的每一行至少对应一个测试。
- 重点覆盖竞态场景：倒计时中房主掉线、结算时用 token 重连、同一 token 同时建立两个连接、宽限期恰好在阶段切换的瞬间到期。

**回归脚本** `npm run sim`：
1. 在随机端口启动真实服务端。为了让回归跑得快，默认一局 15 秒（通过环境变量 `MATCH_SECONDS` 调整，生产环境固定为 60 秒）；加上 `--full` 可以跑完整的 60 秒。
2. 机器人 A 通过 HTTP 建房，机器人 B 按房间码加入。
3. 两人准备，A 开始。
4. 对局中两个机器人随机转向、冲刺，并故意发送重复和过期的 seq。
5. 进入结算后，脚本做以下断言：
   - 两端收到的结算结果完全一致；
   - 各自从快照和增量重建出的地图校验和与服务端给出的 `Result.sum` 相同；
   - `pong.dropped` 恰好等于故意注入的非法输入数；
   - 没有任何旧 tick 被接受。
6. 点「再来一局」，断言房间回到 lobby 且 `round = 2`，再跑一局，确认 tick 重置后能被正确处理。

后续里程碑会给 sim 增加更多场景：M2 增加 `--scenario refresh`（对局中断开 B，再用 token 重连，断言恢复全量状态并继续参与结算）；M4 增加 `--lag 200` 和 `--chaos`。

sim 还支持 `--url https://…` 参数，可以直接对线上部署做冒烟测试。

**持续集成**（M5）：添加 GitHub Actions，在每次推送时运行 `npm run verify`。

**日志**：服务端对房间事件输出单行 JSON 日志，包括建房、加入、离开、断线、重连、阶段切换和结算，方便在 Render 控制台中排查问题。

## 11. 决策记录

**D-01 玩家之间可以互相穿过，没有碰撞。**
选这个规则，一是一句话就能讲清楚；二是更关键的原因：不需要在不同时间线之间判定碰撞。预测时自己处在"未来"，看到的别人处在"过去"，如果有碰撞规则，弱网下会出现"明明没撞到却被判撞上"的问题，而穿过规则从根上消除了这类分歧。冲刺撞人眩晕这种互动玩法，等到 M3 之后、确有余力时再评估。

**D-02 服务端权威，固定 20 Hz tick，客户端只发输入。**
这样从结构上杜绝了伪造位置和分数，也让两端看到的结果只有一个来源。代价是需要做插值和预测来弥补手感，这放在 M4 处理。

**D-03 规则写成确定性纯函数，放在 shared，全部用整数。**
同一份代码同时用于服务端模拟、客户端预测和单元测试；用整数可以避免浮点运算在不同环境下结果不一致。

**D-04 消息用 JSON，不用二进制。**
每个 tick 每个客户端不到 300 字节，一间 4 人房的出站流量约 25 KB/s，带宽不是瓶颈；而 JSON 便于调试和评审直接阅读消息。如果以后需要优化，可以把 `cells` 和 `players` 改成定长数组。

**D-05 增量包含"变化的格子 + 全部玩家状态"，房间元数据变化时单独全量下发。**
玩家最多 4 人，每次全量发送比做差分更简单可靠；房间元数据变化很少，全量下发也免去了合并逻辑。

**D-06 同步正确性靠三层保证：`(round, tick)` 必须连续、定期校验和比对、resync 兜底。**
ws 基于 TCP，同一条连接上不会丢包或乱序。所以"丢弃旧 tick"真正要防的，是重连时快照与增量交错、跨局时 tick 归零，以及调试用的 chaos 注入。校验和用来发现上述三种机制都没有覆盖到的未知 bug，并让客户端自愈。

**D-07 seq 按连接计数，每个新连接从 1 开始。**
如果按玩家全局递增，刷新页面后客户端会从 1 重新计数，之后所有输入都会被当成重复丢弃。旧连接一旦被关闭，它迟到的消息不会再被处理，所以按连接计数是安全的。

**D-08 延迟补偿采用"输入带目标 tick + 服务端输入缓冲"，不做服务端回溯。**
输入里多带一个 `tick` 字段，只是在声明"我希望这个输入在哪个 tick 生效"，仍然是输入，不涉及位置。服务端对这个 tick 做了钳制：最早是下一个 tick，最晚是 10 个 tick 之后，所以客户端无法把输入塞回过去，只能推迟自己的操作，不存在作弊空间。和"回溯重算"相比，它不需要保存历史状态，也不会改写已经广播出去的格子。M1–M3 阶段不填这个字段，服务端收到后立即应用。

**D-09 身份（playerId 和 token）存在 sessionStorage，按房间码分别保存；昵称存在 localStorage。**
这样同一浏览器的两个标签页就是两个人。已知的坑：Chrome 的"复制标签页"会连 sessionStorage 一起复制，导致两个标签共用一个身份。这由"同一 token 来了新连接就顶替旧连接"兜底，被顶替的页面会提供「以新玩家加入」。

**D-10 宽限期分两种：座位保留 30 秒，单人检测 10 秒。**
一局只有 60 秒，如果等满 30 秒才判定"只剩一人"，剩下的玩家要独自跑半局，体验很差；而刷新页面通常 2 秒内就能回来，10 秒足够。如果剩余玩家是因为别人主动离开才落单的，就不再等待，立即结算。

**D-11 房主负责开始，房主自己不需要准备；「再来一局」等于回到大厅并自动准备。**
房主手动开始，可以避免还在等第三个人时被意外开局，也让房主移交有实际意义。房间回到大厅时，没点「再来一局」的人仍然停留在结算页（只是界面状态，服务端已经在 lobby），不会被强行切走。

**D-12 中途加入的人以观战身份进入，下一局按加入顺序补位；满员时也允许观战。**
这符合"不打断正在进行的对局"的原则。观战者能看到完整画面，这本身就是一种邀请体验。

**D-13 已离开玩家的格子保留在地图上，但他们不参与胜负。**
如果把这些格子清空，地图会突然大面积变化，让人困惑；保留格子但取消参赛资格，规则更简单，也更容易解释。

**D-14 前端不用 UI 框架，只用原生 DOM 和 Canvas 2D。**
界面只有四个简单页面，引入框架的收益很小，反而增加依赖和构建复杂度。所有文本都通过 `textContent` 输出，天然防 XSS。

**D-15 单进程同端口，房间放在内存里；Render 免费单实例，新加坡区域，M1 结束就先部署一次。**
单实例正好满足"房间都在同一个进程里"的前提。新加坡区域离亚洲的评审更近。之所以在 M1 就部署，是为了尽早暴露平台层面的问题，例如 wss、代理、端口和冷启动。重启后房间丢失这一点会在 README 中写明。

**D-16 房间码为 5 位，从 31 个字符里选：`23456789ABCDEFGHJKMNPQRSTUVWXYZ`。**
排除了 0、O、1、I、L 这些容易混淆的字符，共约 2860 万种组合，配合按 IP 限流足以抵御猜测。输入时不区分大小写，并自动去掉空格和连字符。

**D-17 构建方式：Vite 构建 client，esbuild 把 server 和 shared 打成单文件；Render 上构建和启动分开。**
单文件避开了 workspace 下 ESM 路径解析的麻烦。本地 `npm start` 包含构建，方便"`npm install && npm start` 一步跑起来"；Render 上的启动命令只运行构建产物，避免每次启动都重新构建。

**D-18 弱网模拟放在客户端，并保持消息顺序；乱序和重复注入单独用 `chaos` 开关。**
真实的 TCP 不会乱序，所以默认的 lag 模拟保持顺序才符合实际；而演示丢弃逻辑需要专门制造异常，就交给 `chaos` 开关。`lag` 的数值表示附加的往返延迟。

**D-19 色盲友好：用 Okabe-Ito 配色，同时叠加形状、昵称和地块纹理四重编码。**
不只依赖颜色区分玩家，评审的要求也明确了这一点。

**D-20 MVP 不做的内容。**
账号、排行榜、匹配、聊天、多实例扩展、持久化、外挂检测、自定义房间设置（地图大小和时长）。

**D-21 提前结算（掉线或离开导致不足 2 人）时仍按当前格数判胜负，不自动判留下的人获胜。**
规则只有一条"格子多的人赢"，提前结算不引入第二条规则，结算页写明原因即可。这样也不会出现"故意拔网线让对方提前结束"能改变胜负的情况：掉线者的格子保留、仍参与排名（主动离开者除外，见 D-13）。

**D-22 断线体验：客户端带 token 自动重连，复用当前画面；"掉线"提示延迟 1.5 秒。**
意外断线（关闭码不是 4001/4002/4008）时，客户端保留当前画面，顶部显示"连接中断，正在重连…（第 n 次）"，按 0.5/1/2/4 s 退避重连，30 秒后放弃并给出「重新加入」。浏览器触发 `online` 事件时立即重试。其他人这边，掉线提示延迟 1.5 秒：刷新页面这种秒回的情况不弹任何提示，只有真正掉线才提示，并在对局画面顶部显示"xx 掉线，重连中 25s"和"在线玩家不足 2 人，8s 后结束本局"（服务端在 RoomView 中下发 `soloEndsAt`，倒计时以服务端为准）。

**D-23 游戏感反馈全部由服务端状态的差异驱动，只有按键音效例外。**
客户端为特效单独维护一份"影子棋盘"，每收到一个权威 tick 就比较前后差异：新染的格子播放弹出动画和粒子；自己覆盖别人的格子时，粒子更多并播放另一种音效；自己的格子被覆盖时播放低音；冲刺开始、冷却结束、领先者变化，也都从状态差异推导出来。这样特效永远和真实结果一致，不会出现"本地放了庆祝、服务端其实没算"的情况。收到快照（加入、重连、resync）时只同步影子棋盘，不播放特效，避免重连瞬间整屏格子一起闪。唯一的例外是按键音效：转向的"嗒"一声和冷却已好时的冲刺音效会在按下时立即播放（服务端确认时不再重复），因为操作反馈的延迟比画面延迟更容易被察觉。

**D-24 反超提示要防抖：领先者需稳定 0.5 秒，两次提示至少间隔 2 秒。**
比分胶着时领先者可能每个 tick 都在变，直接提示会刷屏。规则是：并列不算领先；新领先者保持 0.5 秒才确认；本局第一个领先者不提示（不算反超）；自己反超播放上行音阶，被反超播放下行音阶；观战者看到中性的"xx 反超！"。

**D-25 结算节奏：时间到 → "时间到！"停留 1.1 秒 → 结算卡、分数滚动、彩带和音效。**
直接弹结算会显得仓促，先用一句"时间到！"收住这一局。赢家和平局者看到大量彩带，观战者看到少量彩带，输家只有一段柔和的下行音，不放彩带。刷新页面直接进入结算页时不重播庆祝，只显示结果。最后 10 秒，计时器每秒跳动一次，并配合心跳音（最后 3 秒音调更高），棋盘外圈出现红色呼吸光，第 10 秒时弹出"最后 10 秒！"。

**D-26 音频和动效的边界：首次手势才创建 AudioContext；静音偏好存在 localStorage；尊重"减少动态效果"。**
浏览器的自动播放策略要求音频在用户手势之后才能启动，而创建房间、加入房间都是点击操作，所以进入对局之前一定已经解锁。静音是设备层面的偏好，跨标签页共享是合理的，所以存在 localStorage，和身份信息分开。大厅和对局 HUD 都有静音按钮，也可以按 M 键切换。系统开启"减少动态效果"时，粒子、拖影、彩带和染色弹出动画都会关闭，红色呼吸光改为静态描边。所有音效由振荡器、噪声和包络现场合成，再经过一个压缩器，避免多个音效叠加时爆音。

**D-27 提供 `scripts/bots.ts`，一个人也能验收多人局。**
`npm run bots -- 房间码 3` 会往房间里加 3 个机器人：它们自动准备，对局中绕开墙壁移动、偶尔冲刺，结算后自动再来一局；意外断线时带 token 重连，Ctrl+C 退出时主动发送 leave。它只通过公开协议发送输入，和真人客户端走的是同一条路径，因此也可以对线上地址使用（`--url`）。本地开发时，sirv 在非 production 环境下每次请求都会重新读取文件元数据，避免"服务不停、只重新构建"时浏览器一直拿到 304、继续用旧页面。
