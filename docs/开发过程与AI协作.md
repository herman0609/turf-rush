# 开发过程与 AI 协作

这个项目从需求到上线约 2 小时 10 分钟（2026-10-22 18:36 收到需求，20:44 完成 M5）。代码、测试、脚本和文档都由 AI 编码代理（Manus，运行在开发者本机）编写；人负责定方向、做取舍，并在每个里程碑验收。这份文档说明分工、时间线、让 AI 产出可靠的具体做法，以及哪些内容被有意砍掉了。

## 分工

**人（Herman）**：给出产品目标、玩法、技术方向、同步和生命周期的硬性要求、里程碑划分和验收节奏（每个里程碑都要先确认构建和测试通过，再给出手动验证步骤，然后提交）。在关键节点做决定：部署平台选 Render，仓库改为公开，提供部署凭证。

**AI**：读需求、出方案（[DECISIONS.md](DECISIONS.md) 初稿：目录结构、消息协议、状态机、风险最高的三个点、里程碑、阻塞问题），确认后按里程碑实现。它自己跑测试，在内置浏览器里开两个标签页实际对战并截图检查画面，再通过 API 部署，并对线上地址做冒烟测试。

## 让 AI 产出可靠的做法

1. **先方案，后代码。** 动手前先把协议字段、状态机和每个生命周期事件的处理方式写清楚，由人确认。之后的实现基本没有返工，偏离方案的地方都回写到 DECISIONS 里，并说明原因。
2. **规则写成纯函数，并配单元测试。** `step(state, inputs)` 是确定性的，服务端模拟和客户端预测共用同一份代码。AI 每次修改都有测试兜底，两端也不会各写一套而不知不觉地出现分歧。
3. **每个里程碑都是一个可验证的闭环。** `npm run verify` 依次做类型检查、99 个测试、构建和回归脚本；再加上浏览器里两个标签页实际对战并截图。两者都通过，才算完成。
4. **回归脚本相当于 AI 的眼睛。** 两个机器人走和真人完全相同的公开协议，跑完整的两局，断言所有端的结算一致、各自重建的地图校验和与服务端一致，并且没有 tick 缺口。每次改动后都跑一遍，也能直接对线上地址跑。
5. **进度笔记。** 关键状态（凭证位置、部署 ID、待办事项）写在不进 Git 的本地笔记里，避免长会话中上下文被压缩后丢失信息。
6. **凭证处理。** token 存在不进 Git 的本地文件里，推送时只在当次命令中使用，不写进 Git 配置。推送前扫描了整个 Git 历史，确认没有凭证泄露。

## 实测中发现并修复的问题

下面这些问题都不是单元测试发现的，而是在浏览器实测、对比截图或核对线上状态时发现的：

| 阶段 | 现象 | 原因与修复 |
|---|---|---|
| M1 | 角色贴边时，头顶昵称被裁掉一半 | 昵称标签限制在画布内，角色在顶行时改画到下方 |
| M2 | 刷新页面时，对方屏幕上会闪一下"掉线" | 掉线提示加 1.5 秒防抖；正常刷新会在这之前重连成功 |
| M2 | 窗口较小时，结算卡被棋盘和提示条挡住 | 结算层改为全屏覆盖，提示条移到底部 |
| M3 | 重新构建后，浏览器仍然显示旧页面 | sirv 缓存了文件元数据，ETag 不变导致一直返回 304；非生产环境改为每次请求重新读取（D-27） |
| M4 | 开启抖动模拟后，调试面板显示有断档，但服务端没有拥塞记录 | 弱网模拟器自己把消息打乱了顺序（setTimeout 取整）；改成单一 FIFO 队列（D-31） |
| M4 | 在 `?chaos` 下，几乎每次乱序都会触发一次全量快照 | 改为先在 4 个 tick 的窗口内重排，补不齐再请求快照（D-30） |
| 部署 | 推送 M4 后，线上一直是旧版本 | 服务没有接入 GitHub App，自动部署不会触发；改为通过 API 指定 commit 部署，并在冒烟测试前核对线上引用的构建产物文件名 |
| 部署 | 回归脚本对线上地址运行时超时 | 远程模式仍按本地 5 秒一局的时长等待；改为按线上的 60 秒等待 |

## 范围控制

**顺序**：先做完整闭环（M1），再做生命周期（M2）、游戏感（M3），最后做延迟优化（M4）。最重要的风险（端到端能不能跑通）最先验证；部署原计划放在 M1 之后，因为当时还没拿到凭证，推迟到 M3 之后。

**按需求明确不做的**：账号、排行榜、匹配、聊天、多服务器扩展。

**计划内、但被砍掉或换了做法的**（DECISIONS 中都有说明）：
- 调试面板上的操作按钮：改用 URL 参数注入弱网和乱序，并由自动化测试覆盖。面板只做展示，不需要额外的调试协议。
- 回归脚本里的弱网场景：改由 `prediction.test.ts` 覆盖，它用真实的 Room 加模拟延迟，断言 RTT 200 ms 和 600 ms 下都零纠正。这样更快、更稳定，也能精确断言。
- GitHub Actions CI：配置已经写好（[`docs/ci/verify.yml`](ci/verify.yml)），但当前 token 没有 `workflow` 权限，GitHub 不允许它创建工作流文件，所以还没有启用。

**有意的简化**：房间只存在单个进程的内存里（重启即丢失，有明确提示）；运行在 TCP 上，不做 UDP 式的丢包补偿；手机触屏只做了代码路径检查，没有真机验证。
